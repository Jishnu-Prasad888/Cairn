# Sharing

Implemented as part of the authorization phase. Public shares let anyone with
the share token access a specific resource subtree without an account.

## Public share links

- The token is a cryptographically random 256-bit value (base64url) generated by
  the server. Internal database IDs are never used as security credentials.
- The raw token is returned **exactly once** (on creation); only its SHA-256
  hex digest is stored server-side.
- Optional expiration (`expires_at`, RFC3339). A share is dead after that
  instant and the token stops working.
- Optional password protection (min 8 characters when set). Passwords are
  hashed with the same scheme as account passwords and verified on every use.
- Fine-grained capabilities selected from the same capability set as grants:
  `read`, `download`, (and `create`/`edit`/`delete` for editors where
  appropriate — enforcement is the same as for grants).
- Revocation (`DELETE`); a revoked share stops being accessible to the token
  immediately.
- Audit rows are written for share creation, revocation, and use.

## Semantics

Shares reference resources (a library, folder, album, memory...) via the same
resource keys as grants. A share scopes its capabilities to **the shared
resource and its subtree** — it can never grant access above the share root.
Requests identify the share by the token in the URL path and optionally supply
the password via the `X-Cairn-Share-Password` header.

Access still flows through the same authorization evaluation as everything else:
a public request must satisfy **both** the share's capabilities **and** the key
being covered by the share's resource key (`shareCan = caps.All(...) &&
coversKey(resourceKey, key)`). Shares never bypass permission evaluation; they
are an alternative principal with an explicit scope.

## API

- `GET    /shares/{token}` public share info (who it is, what library it covers,
  whether a password is required).
- `POST   /shares/{token}/authenticate` verify the token + password.
- `GET    /shares/{token}/files[?folder=]` list files under the share root.
- `GET    /shares/{token}/files/{fileID}` file metadata.
- `GET    /shares/{token}/files/{fileID}/download` file bytes (requires
  `download` capability).

Admin-side management lives under `/libraries/{libraryID}/shares` and requires
`share` or `manage` on the library: `GET` list, `POST`
(`{key, caps, password?, expires_at?}` → returns `{share, token}`), `DELETE`
revoke. Responses exclude actionable revocation of other users' links unless the
actor has `manage`.

## Semantics notes

- Listing a folder *above* the share root returns 403 (the scope is the shared
  subtree only).
- Wrong password, missing password, expired share, revoked share, and unknown
  token all return 401 `CairnErrUnauthorized` — the server does not reveal which
  condition failed.
